## Цел

В prod режим Analyst чете реални тикети от Jira (`myposgroup.atlassian.net`) през официалния
Atlassian Remote MCP Server, със **същия инструмент** `get_ticket_details(ticket_id)` (име,
сигнатура, формат на картата) като в demo, плюс `search_tickets(jql)`. Write-back (коментар в тикета
с PR линковете) е подготвен като метод, но се използва от `finalize` едва в PR 3.

## Контекст / входове

- Проверени на живо (в планирането): endpoint `https://mcp.atlassian.com/v1/mcp`; `cloudId` приема
  hostname; `getJiraIssue` с `responseContentFormat: "markdown"` връща `fields.description` като чист
  текст; `searchJiraIssuesUsingJql` връща `{"issues": {"nodes": [...]}}`; грешките са
  `{"error": true, "message": ...}`; необвързан JQL се отказва.
- `mcp==1.29.1` (официален Python SDK) — инсталиран в venv, `ClientSession` + `streamablehttp_client`
  / `stdio_client` се импортират.
- Графът е синхронен → sync мост около async MCP клиента (нишка + `asyncio.run(wait_for(...))`).
- Конвенции: инструментите връщат грешки като текст; lazy import на `mcp` (demo не го изисква);
  тестовете не пипат мрежа (fake `call_tool`).

## Рискове / допускания

- API token на потребителя (`JIRA_EMAIL` + `JIRA_API_TOKEN`) — нужни за ръчната проверка; без тях
  proверката остава за потребителя (описана в README).
- Форматът на MCP отговорите може да се променя — нормализацията е защитена (fallback към raw текст),
  а картата винаги има секцията „Критерии за приемане" (с бележка, ако липсват).
- Windows: `npx` за oauth варианта е `npx.cmd` — `stdio_client` от SDK го решава; проверява се ръчно.
